# Running the game locally

The game is one Node process: no containers, no generated config, and no port
allocator beyond one port per worktree.

## Prerequisites

Node 24 (`.nvmrc`), and `npm ci`. That is the list.

## Starting it

```bash
npm run dev
```

Mock narration, no network, no API key. `npm run dev:ai:free` and
`npm run dev:ai:paid` start the same server with a real model, reading
`.env.ai.free.local` / `.env.ai.paid.local` from the config root.

Switching between them is switching command. There is nothing to reseed and
nothing to restart, because a profile is env, not a database row.

`npm run prod` is the same server pointed at the persistent database rather
than this checkout's, with `prod:ai:free` and `prod:ai:paid` alongside. Model
and database are orthogonal: `--db <name>` sets the database for any of them.

## Where your data lives

| | |
|---|---|
| Databases | `$MYSTERY_CONFIG_ROOT/database/<name>/game.db` (gitignored) |
| Blueprints | `$MYSTERY_CONFIG_ROOT/blueprints/`, then the repo's `blueprints/` |
| Images | `$MYSTERY_CONFIG_ROOT/blueprint-images/` |
| Env | `.env.local`, `.env.ai.<mode>.local`, `.env.images.local` in the config root |

`MYSTERY_CONFIG_ROOT` is an absolute path that moves all of it outside the
repo, so several clones and worktrees share one set of blueprints and images
and survive a checkout being deleted. Unset, everything resolves from the repo
root.

Nothing in the tests writes to your databases. The suites start the server
against a temporary config root and delete it afterwards.

## Which database

Content is shared across worktrees; databases are not.

| | |
|---|---|
| `npm run dev` | `database/<worktree name>/game.db`, or `main` in the main checkout |
| `npm run prod` | `database/prod/game.db` |
| `--db <name>` | `database/<name>/game.db` |
| the suites | a `test` database in a temporary config root, deleted after |

A database is the one thing here carrying a schema version. `MIGRATIONS` is
forward-only and keyed on `PRAGMA user_version`, and `openDatabase()` refuses a
file whose version is ahead of the code — so a branch that bumps
`SCHEMA_VERSION` against a shared file locks every other checkout out of it.
`lib/database-target.mjs` derives the name from the worktree directory, the
same identity the port comes from, so neither moves when you switch branches.
That name is generated by whatever created the worktree and is rarely pretty;
`--db <name>` or `MYSTERY_DATABASE` gives this checkout a better one.

## Managing them

```bash
npm run db:init                       # create this checkout's
npm run db:list                       # all of them: schema, row counts, size
npm run db:reset                      # empty it and start again
npm run db:copy -- prod               # play against a copy of your history
```

Names default to this checkout's, including `db:copy`'s destination — a
worktree's name is generated rather than chosen, so nothing makes you type it.
`prod` needs `--force` to reset or overwrite.

Opening a database is the migration — `openDatabase()` applies whatever
`MIGRATIONS` has not been applied yet — so `npm run db:init -- <name>` migrates
an existing one without starting the server, and reports the version it moved
from. Take a copy of `prod` before a schema bump lands: the steps are
forward-only, and there is nothing to undo one with.

`db:copy` snapshots through SQLite's backup API, so it is safe while the game
is writing. `cp` is not: committed transactions may still be in the `-wal`.

## Worktrees

Each worktree gets its own port so two checkouts can run side by side:

```
web   51000 + slot     slot = hash(worktree name) % 1000 + 1
```

`lib/worktree-ports.mjs` derives it. The main checkout uses 51000. The database
is named from the same worktree, and the two together are the whole of the
isolation.

The profile cookie is named for the database rather than fixed, because a port
is not part of a cookie's identity: `localhost:51000` and `localhost:51006`
share one jar, and so do `npm run dev` and `npm run prod`, which run on the
same port against different databases. With one fixed name, signing in to
either overwrote the other, and the loser then answered 401 to every request
while the page still showed a signed-in menu. Each database now has its own
cookie, so you stay signed in to all of them at once.
`packages/game-engine/src/player-cookie.ts` derives the name.

## Poking at the database

It is a SQLite file, so the usual tools work while the game is running (WAL
mode is on for exactly this reason):

```bash
sqlite3 "${MYSTERY_CONFIG_ROOT:-.}/database/prod/game.db" "select id, mode, outcome, updated_at from game_sessions order by updated_at desc limit 10;"
```

`npm run db:list` prints the path of each database and marks the one this
checkout resolves to.

To pull one session out as a self-contained artifact for the evaluation
pipeline:

```bash
npm run eval:trace:extract -- --session <id>
```

That reads the database directly, so the game does not have to be running, and
`--db <file>` points it at a copy.

## Troubleshooting

**Something is already listening on the port.** Another checkout of this repo,
or a server left running from a previous session. The test runner detects this
and fails with a clear message rather than testing against the wrong server;
for `npm run dev`, stop the other one.

**`better-sqlite3` failed to install.** It ships prebuilt binaries for macOS,
Linux, and Windows on x64 and arm64, so this should not happen — but if a
platform has no prebuild, npm falls back to compiling and needs a toolchain.

**The database is from a newer version of the engine.** `openDatabase()`
refuses to open a file whose `PRAGMA user_version` is ahead of the code rather
than corrupting it. This should now only happen to `prod`, which every branch
opens: update the checkout to one that understands the schema. For a worktree's
own database, `npm run db:reset` starts it again from scratch.

**Blueprint edits are not showing up.** The content cache is keyed on mtime and
size, so a saved edit is picked up on the next request. If you replaced a file
with one of identical size in the same millisecond, touch it.
